## 1. CameraSource 类结构总览

先看头文件 `include/rkfast/camera_source.hpp` 的整体结构：

```cpp
class CameraSource {
 public:
  // ========== 对外接口（3 个函数） ==========
  explicit CameraSource(const AppConfig& config);   // 构造：接收配置
  ~CameraSource();                                   // 析构：自动关相机

  bool Open(std::string* error);                     // 打开相机，开始采集
  void Close();                                      // 关闭相机，停止线程
  bool ReadLatest(cv::Mat* frame,                     // 读取最新一帧
                  double* timestamp, uint64_t* seq) const;

 private:
  // ========== 内部实现（1 个函数 + 一堆成员变量） ==========
  void CaptureLoop();                    // 采集线程的主循环

  AppConfig config_;                     // 配置副本
  mutable std::mutex mutex_;             // 互斥锁：保护 latest_
  cv::VideoCapture cap_;                 // OpenCV 的相机对象
  cv::Mat latest_;                       // 最新帧缓存（C++ Mat 就是图像）
  double timestamp_ = 0.0;               // 最新帧的时间戳
  uint64_t seq_ = 0;                     // 帧序号
  std::atomic<bool> stop_{false};        // 退出标志（原子变量，线程安全）
  std::thread thread_;                   // 采集线程对象
};
```

设计哲学：**对外 3 个函数，对内 1 个线程**。调用者只需要知道 Open → Read → Close，不需要知道里面有个线程在跑。

### 成员命名约定

注意看 private 成员有特殊的命名习惯：

| 后缀/前缀 | 含义 | 例子 |
|-----------|------|------|
| `_` 后缀 | 私有成员变量 | `config_`, `latest_`, `seq_`, `thread_` |
| 无后缀 | 公开成员或局部变量 | `Open()`, `ReadLatest()` |

这不是 C++ 语言规定，是**编码规范**——让你一眼看出变量是不是私有成员。你项目中全程遵守这个约定。

## 2. 构造函数和析构函数

```cpp
// 构造函数：接收 AppConfig，用初始化列表存起来
CameraSource::CameraSource(const AppConfig& config) : config_(config) {}

// 析构函数：直接调 Close，保证相机一定被关闭
CameraSource::~CameraSource() { Close(); }
```

### 2.1 构造函数里的 explicit

```cpp
explicit CameraSource(const AppConfig& config);
//  ↑ explicit = 禁止隐式类型转换
```

`explicit` 的意思是：你不能把 AppConfig "悄悄"变成 CameraSource。看一下如果没有 explicit 会发生什么：

```cpp
// 如果没有 explicit：
void take_photo(CameraSource cam) { ... }

AppConfig config;
take_photo(config);   // 编译器会自动把 config 构造成 CameraSource！
                      // 这个叫"隐式转换"，非常容易产生意外的 bug
```

有了 explicit，你就必须显式构造：

```cpp
take_photo(CameraSource(config));  // 显式构造，意图清楚
```

**规则**：单参数的构造函数一律加 `explicit`，预防隐式转换的坑。

### 2.2 初始化列表

```cpp
CameraSource::CameraSource(const AppConfig& config) : config_(config) {}
//                                  ↑ 参数         ↑ 初始化列表（config_ = config）
```

`:` 后面叫**初始化列表**。效果等价于在函数体里写 `config_ = config`，但更高效（少一次默认构造 + 赋值的过程）。

**为什么 config_ 是传值进来的副本？** 因为 CameraSource 拿着 config 在独立线程里用，万一外部改了原始 config 怎么办？直接拷贝一份进来，两清。

### 2.3 析构函数的 RAII 哲学

```cpp
CameraSource::~CameraSource() { Close(); }
```

析构函数就做一件事：调 `Close()`。这就是 RAII（Resource Acquisition Is Initialization，资源获取即初始化）——说人话就是：

> **构造时获取资源，析构时释放资源。你不需要手动记得关。**

```cpp
// 使用方式：对象出了作用域自动销毁，自动关相机
{
    CameraSource cam(config);
    cam.Open(&error);
    // ... 采集几十万帧 ...
}   // ← 离开这个花括号，cam 的析构函数自动调 Close()
    // 你永远不会忘记关相机
```

对比 C 语言的风格：

```c
// C 风格：必须记住手动关
CameraSource* cam = camera_open(config);
// ... 采集几十万帧 ...
camera_close(cam);  // ← 如果这里前面有个 return 或者异常跳出了怎么办？
                    // 忘了关 → 资源泄漏 → 第二次打开相机失败
```

## 3. Open 函数精讲

这是 CameraSource 最核心的函数，我们逐段拆解。

### 3.1 V4L2 优先 → 退回到 CAP_ANY 的策略

```cpp
bool CameraSource::Open(std::string* error) {
  // 第一步：根据配置选择 API
  const int api = config_.use_v4l2 ? cv::CAP_V4L2 : cv::CAP_ANY;

  // 第二步：尝试用首选 API 打开
  if (IsDigits(config_.camera)) {
    cap_.open(std::stoi(config_.camera), api);   // 纯数字 → 当成设备索引（0, 1, 2...）
  } else {
    cap_.open(config_.camera, api);               // 非纯数字 → 当成设备路径（/dev/video73）
  }

  // 第三步：如果首选 API 打不开，退回到 CAP_ANY 再试一次
  if (!cap_.isOpened() && api != cv::CAP_ANY) {
    if (IsDigits(config_.camera)) {
      cap_.open(std::stoi(config_.camera), cv::CAP_ANY);
    } else {
      cap_.open(config_.camera, cv::CAP_ANY);
    }
  }

  // 第四步：还是打不开？报错退出
  if (!cap_.isOpened()) {
    if (error != nullptr) {
      *error = "could not open camera: " + config_.camera;
    }
    return false;
  }
  // ... 后面还有设置参数和启动线程 ...
}
```

**为什么 V4L2 优先？** 这块板子是 Linux 嵌入式的 RK3576，摄像头驱动是 V4L2（Video For Linux 2）框架。用 `cv::CAP_V4L2` 直接告诉 OpenCV 走 V4L2 路径，性能最好。如果某个摄像头 V4L2 不兼容，`cv::CAP_ANY` 作为兜底——让 OpenCV 自己选后端。

**为什么有 IsDigits 判断？** 因为 `config_.camera` 可能是两种东西：
- 设备路径：`/dev/video73`（Linux 设备节点）
- 设备索引：`0`（第 0 号摄像头）

`cap_.open(0, api)` 和 `cap_.open("/dev/video73", api)` 是 OpenCV 的两种打开方式。代码里用 `IsDigits()` 判断传来的字符串是不是纯数字来区分。

### 3.2 IsDigits 辅助函数

```cpp
namespace {

bool IsDigits(const std::string& value) {
  return !value.empty() &&
         std::all_of(value.begin(), value.end(),
                     [](unsigned char ch) { return std::isdigit(ch) != 0; });
  //                   ↑ 这是一个 lambda 表达式（第 10 章会讲）
  //                   现在你理解成：对每个字符 ch，检查它是不是数字
}

}  // namespace
```

`std::all_of` 是 STL 算法：检查一个范围内的**所有元素**是否都满足某个条件。这里检查字符串里每个字符都是数字。

`[](unsigned char ch) { return std::isdigit(ch) != 0; }` 是 lambda（匿名函数）——检查单个字符是不是数字。第十章的 `RknnDetector` 里你会遇到更多 lambda，现在先跳过细节。

**等价于 C 语言的：**

```c
int is_digits(const char* value) {
    if (value == NULL || *value == '\0') return 0;
    for (int i = 0; value[i] != '\0'; i++) {
        if (!isdigit((unsigned char)value[i])) return 0;
    }
    return 1;
}
```

C++ 版本一行搞定，但没有更"本质"的差别——只是写法更紧凑。

### 3.3 设置相机参数

```cpp
  // 四字符码（FOURCC）：指定视频编码格式
  if (config_.fourcc.size() >= 4) {
    cap_.set(cv::CAP_PROP_FOURCC,
             cv::VideoWriter::fourcc(config_.fourcc[0], config_.fourcc[1],
                                     config_.fourcc[2], config_.fourcc[3]));
  }

  // 分辨率
  cap_.set(cv::CAP_PROP_FRAME_WIDTH,  config_.width);   // 640
  cap_.set(cv::CAP_PROP_FRAME_HEIGHT, config_.height);   // 480

  // 帧率
  cap_.set(cv::CAP_PROP_FPS, config_.fps);               // 60

  // 缓冲区大小 = 1（关键！）
  cap_.set(cv::CAP_PROP_BUFFERSIZE, 1);
```

逐行解释：

**FOURCC（Four Character Code，四字符码）:**

相机传过来的视频数据可以是不同编码格式的：MJPEG（压缩的）、YUYV（未压缩）、H264（高度压缩）。`"MJPG"` 这个四字符码告诉相机："给我传 MJPEG 格式"。为什么选 MJPG？同样一根 USB 线，YUYV 640x480@60fps 带宽不够，MJPG 640x480@60fps 就能跑——因为压缩了。

`cv::VideoWriter::fourcc('M', 'J', 'P', 'G')` 把 4 个字符拼成一个整数，交给驱动识别。OpenCV 在帮你做这个拼接。

**缓冲区大小 = 1 的用意：**

这是整段代码里最重要的细节。

```
BUFFERSIZE = 3（默认）：      BUFFERSIZE = 1（我们设置的）：
┌───┬───┬───┐                ┌───┐
│ 1 │ 2 │ 3 │   ← 驱动缓存     │ 3 │   ← 只有一个槽位
└───┴───┴───┘                └───┘
  ↑               ↑
  你读到第 1 帧     此时第 5 帧       你读到的永远是摄像头的当前帧
  摄像头已拍到第 5 帧了             虽然可能丢帧，但绝对是最新的
```

当 BUFFERSIZE > 1 时，驱动内部有一个队列。如果你读得慢，等你读到第 1 帧的时候，第 5 帧已经到了。你拿到的是 1 帧前的数据——在打靶场景里，这就是瞄准落后了。

BUFFERSIZE = 1 的意思是：驱动只保留最新的一帧，新的来了旧的就丢掉。这保证了 **ReadLatest 拿到的永远是摄像头此时此刻传过来的最新帧**。

丢旧帧是一个**权衡**：宁可丢帧，也不能用旧数据。打靶场景对实时性要求极高，旧帧等于延迟。

### 3.4 启动采集线程

```cpp
  // 重置退出标志
  stop_.store(false);

  // 启动采集线程
  thread_ = std::thread(&CameraSource::CaptureLoop, this);

  return true;
}   // Open 函数结束
```

这一行创建了一个独立线程：

```cpp
thread_ = std::thread(&CameraSource::CaptureLoop, this);
//                    ↑ 成员函数指针                 ↑ this = 当前对象
```

`&CameraSource::CaptureLoop` 是成员函数指针。传递成员函数给线程时，必须同时传 `this`——因为成员函数需要知道自己操作的是哪个对象。

Open 调用后：
- 主线程继续往下跑（你的 main 函数）
- 采集线程在后台疯狂循环 `CaptureLoop()`，不停往 `latest_` 里写新帧
- 两个线程并行工作

## 4. 为什么用独立线程采集

这是本章的设计核心。一句话概括：

> **采集和主循环解耦。采集线程只管"把帧拿回来"，主循环只管"用帧做推理和控制"。**

画成图：

```
           ┌─────────────────┐
USB 摄像头─→│ 采集线程         │
           │ CaptureLoop()   │
           │ cap_.read()     │──→ latest_ (共享帧缓存)
           │ cap_.read()     │
           │ cap_.read() ... │
           └─────────────────┘
                   │
          latest_  │  mutex_ 保护
                   ↓
           ┌─────────────────┐
           │ 主线程           │
           │ ReadLatest()    │──→ 送给 RknnDetector 推理 ──→ 送给 RectTracker 跟踪
           │ ReadLatest()    │        ↓
           │ ReadLatest()... │    串口输出角度
           └─────────────────┘
```

如果不用独立线程（采集和推理在同一个循环里）：

```cpp
// 不好的设计：采集和推理串在一起
while (running) {
    cap_.read(frame);           // 等一帧（可能等 16ms）
    auto det = detector->Infer(frame);  // 推理（10ms）
    tracker->Update(det);       // 跟踪（1ms）
    writer->Send(tracker);      // 发送（忽略不计）
}   // 每帧总耗时 = 等帧 + 推理 + 跟踪 ≈ 27ms → 约 37 FPS
```

`cap_.read()` 是阻塞的——它会停下来**等**一帧到达。如果采集和主循环串在一起，等待的时间就浪费了。用了独立线程后：

```cpp
// 好设计：采集和推理并行
// 采集线程：一直在 cap_.read() → 写 latest_
// 主线程：一直在 ReadLatest() → 推理 → 跟踪 → 发送
// 两个线程同时跑，互不等待
```

**注意**：推理线程（DetectorWorker）也是独立的，实际项目里有三个线程：主控制线程 + 采集线程 + 推理线程。但这是后面章节的事。

## 5. CaptureLoop 循环精讲

```cpp
void CameraSource::CaptureLoop() {
  // 可选：设置 CPU 亲和性（把这个线程绑在指定核心上）
  std::string affinity_error;
  if (!config_.camera_affinity.empty() &&
      !BindCurrentThread(config_.camera_affinity, &affinity_error)) {
    std::cerr << "camera affinity warning: " << affinity_error << "\n";
  }

  while (!stop_.load()) {           // 只要没叫停，就一直在循环
    cv::Mat frame;
    if (!cap_.read(frame) || frame.empty()) {
      // 读失败了或帧是空的 → yield 让出 CPU，马上再试
      std::this_thread::yield();
      continue;
    }

    // 拿到有效的帧，写入共享缓存
    std::lock_guard<std::mutex> lock(mutex_);   // 拿锁
    latest_ = std::move(frame);                  // 移动语义：浅拷贝
    timestamp_ = NowSeconds();                   // 记录时间戳
    ++seq_;                                      // 帧序号 +1
  }   // lock 出作用域，自动释放锁
}
```

逐段解释：

### 5.1 主循环条件：stop_ 原子变量

```cpp
while (!stop_.load()) {
```

`stop_` 的类型是 `std::atomic<bool>`。`load()` 是"原子地读取当前值"。为什么不用普通的 `bool`？

因为普通 `bool` 的读写不是原子的：一个线程读、另一个线程写，在 CPU 指令级别可能出现半个字节的情况，读到错误的值。`std::atomic<bool>` 保证读和写操作是原子的——硬件层面保证不会出现半个字节的情况。

**原子（atomic）** = 不可再分的。要么整个读完，要么整个写完，没有"读到一半被写入打断"的情况。

上一章学过 `std::mutex` 也是解决多线程安全问题的。什么时候用哪个？

| 保护对象 | 用什么 | 原因 |
|----------|--------|------|
| 简单的标志位（stop_） | `std::atomic<bool>` | 轻量，无锁，效率高 |
| 复杂数据结构（latest_） | `std::mutex` | 需要保护一个"读-改-写"区域 |

### 5.2 cap_.read() 和 yield

```cpp
    cv::Mat frame;                          // 局部变量，每次循环创建一个新的
    if (!cap_.read(frame) || frame.empty()) {
      std::this_thread::yield();            // 读失败：让出 CPU
      continue;                             // 跳过本次，下轮再试
    }
```

`cap_.read(frame)` 从相机驱动拿一帧，写入 `frame`。返回值 `true` 表示成功，`false` 表示失败（如相机断连、驱动返回错误等）。

如果失败了，`std::this_thread::yield()` 让当前线程**主动让出 CPU 时间片**——不做无意义的重试死循环，把 CPU 让给其他线程（比如主循环线程）。下一轮调度回来时再试。

### 5.3 std::move 移动语义

```cpp
    latest_ = std::move(frame);
```

普通赋值 `latest_ = frame` 会把整张图像**完整复制**一份（640x480x3 字节 ≈ 900KB）。每 60 帧就是 54MB/秒的复制开销——纯浪费。

`std::move(frame)` 是"移动赋值"：把 `frame` 内部的数据指针直接"转移"给 `latest_`，不复制像素数据。转移后 `frame` 变成空的（数据已被搬走），下一轮循环会创建一个新的 `frame`。

```
普通赋值 latest_ = frame：          移动赋值 latest_ = std::move(frame)：
┌──────┐     ┌──────┐              ┌──────┐         ┌──────┐
│frame │ ──→ │latest│              │frame │ ──转移→ │latest│
│ 数据 │ 复制 │ 数据 │  900KB 复制   │ 数据 │  指针传递  │ 数据 │  ≈ 0KB 复制
└──────┘     └──────┘              └──────┘         └──────┘
                                   frame 变空     latest 持有数据
```

这是 C++11 的重要特性——移动语义（move semantics），第 12 章会专门讲。现在记住：**`std::move` = 转移所有权，不复制数据**。

## 6. std::lock_guard 的自动锁机制

这是 RAII 在多线程中的经典体现：

```cpp
{
    std::lock_guard<std::mutex> lock(mutex_);   // 这一行：lock(mutex_)
    latest_ = std::move(frame);                  // 安全写入
    timestamp_ = NowSeconds();
    ++seq_;
}   // lock 对象析构 → 自动 unlock(mutex_)
```

翻译成三句话：

1. **构造时锁定**：创建 `lock_guard` 对象的那一刻，内部调用 `mutex_.lock()`
2. **保护临界区**：`{ }` 花括号之间的代码受锁保护，其他线程进不来
3. **析构时解锁**：离开花括号，`lock` 对象被销毁，析构函数自动调用 `mutex_.unlock()`

**为什么这很重要？** 因为即使保护区域里某行代码抛异常跳出了，析构函数也一定会执行——锁一定被释放。如果你手动写 `mutex_.lock()` / `mutex_.unlock()`，万一中间抛异常，锁就永远挂着了（死锁）。

```cpp
// 不好：手动加锁/解锁
mutex_.lock();
latest_ = frame;        // 如果这一行抛异常？→ 永远 unlock 不了 → 死锁
mutex_.unlock();

// 好：用 lock_guard
{
    std::lock_guard<std::mutex> lock(mutex_);
    latest_ = frame;    // 即使抛异常，lock 析构时一定 unlock
}
```

## 7. ReadLatest —— 为什么只读最新帧

```cpp
bool CameraSource::ReadLatest(cv::Mat* frame, double* timestamp, uint64_t* seq) const {
  std::lock_guard<std::mutex> lock(mutex_);   // 拿锁

  if (latest_.empty()) {
    return false;              // 还没收到过任何帧
  }

  if (frame != nullptr) {
    *frame = latest_;          // 把最新帧拷贝给调用者
  }
  if (timestamp != nullptr) {
    *timestamp = timestamp_;   // 拷贝时间戳
  }
  if (seq != nullptr) {
    *seq = seq_;               // 拷贝帧序号
  }
  return true;
}   // lock 出作用域，自动 unlock
```

### 7.1 为什么用指针参数而不是返回值？

```cpp
// 为什么不这样写？
// cv::Mat ReadLatest();   ← 返回 Mat，又是一次大复制

// 而是这样写？
bool ReadLatest(cv::Mat* frame, ...) const;   ← 通过指针传出，函数返回 bool
```

因为函数只能返回一个值。这里需要同时返回 frame、timestamp、seq 三个东西，用指针参数最直接。

更 C++ 的风格是用 `std::optional` 或 `std::tuple`，但指针参数的写法更接地气——C 程序员一眼就懂。

### 7.2 nullptr 检查

```cpp
if (frame != nullptr) { *frame = latest_; }
if (timestamp != nullptr) { *timestamp = timestamp_; }
if (seq != nullptr) { *seq = seq_; }
```

调用者可能只需要帧，不需要时间戳和序号：

```cpp
cv::Mat frame;
cam->ReadLatest(&frame, nullptr, nullptr);  // 只要图片，不要时间戳和序号
```

nullptr 检查让调用者可以只取自己关心的数据——不用填一些假变量。

### 7.3 "丢旧帧策略"的本质

采集线程每 1/60 秒往 `latest_` 写一帧新数据。主循环每次调 `ReadLatest`，拿到的都是此时此刻 `latest_` 里的值。

```
采集线程：帧1 → 帧2 → 帧3 → 帧4 → 帧5 → 帧6 → ...
主线程：            Read →    Read →    Read → ...
                   拿到帧2   拿到帧4   拿到帧5
```

主线程可能跳过一些帧（帧1、帧3），但拿到的永远是最新的。这就是"丢旧帧策略"——用空间换时间，用"可能丢帧"换"绝对不延迟"。

**为什么不设计成"每帧不漏"的队列？** 因为打靶不需要每帧都处理。如果处理跟不上采集的速度，队列会越堆越长，延迟越来越大。丢掉旧帧，保证每次处理的都是最新的数据。

## 8. Close —— 线程安全退出模式

```cpp
void CameraSource::Close() {
  stop_.store(true);             // 第一步：设置退出标志
  if (thread_.joinable()) {      // 第二步：等待线程结束
    thread_.join();
  }
  if (cap_.isOpened()) {         // 第三步：释放相机资源
    cap_.release();
  }
}
```

这是 C++ 多线程中**最经典的安全退出模式**，分三步：

### 8.1 第一步：stop_.store(true)

`stop_` 是原子变量。写入 `true` 后，采集线程的 `while (!stop_.load())` 下一轮就会看到 true，跳出循环。

为什么用 `store()` 而不是直接赋值？因为 `stop_` 是 `std::atomic<bool>`，它的赋值必须通过 `store()` 方法——这是原子类型的 API 约定。`load()` 读，`store()` 写。

### 8.2 第二步：thread_.join()

`join()` 的意思是"等待这个线程执行完"。主线程停在这里，直到采集线程的 `CaptureLoop()` 函数 return，才继续往下走。

如果不 `join()`，采集线程还在跑，主线程就已经销毁了 `cap_` 和 `latest_`——采集线程会访问已释放的内存，直接崩溃。

**joinable()** 检查线程是否"可等待"——如果线程没有启动、已经 join 过、或者被 detach 了，调用 `join()` 也会崩。先检查再 join 是防御性编程。

### 8.3 第三步：cap_.release()

释放 OpenCV 内部的相机资源。虽然 `cv::VideoCapture` 的析构函数也会做这件事，但显式调用更明确。

### 8.4 这个模式也用在析构函数里

```cpp
CameraSource::~CameraSource() { Close(); }
```

意味着不管谁创建了 CameraSource，只要对象被销毁（出了作用域、程序退出、被 delete），相机会自动关闭、线程自动等待。你永远不会忘。

## 9. cv::VideoCapture 基础用法速查

你项目里用的是 OpenCV 的 VideoCapture 类。这里给一个最简化的调用速查：

```cpp
#include <opencv2/videoio.hpp>

// 1. 打开相机
cv::VideoCapture cap;
cap.open(0);                     // 打开第 0 号摄像头（用索引）
cap.open("/dev/video73");        // 打开 Linux 设备节点（用路径）

}
```

## 10. 与 C 语言对比：如果用 pthread 写会多多少代码

这是本章最有价值的对比。假设用纯 C（V4L2 + pthread）实现同样的功能。

### C 版本（V4L2 + pthread，简化版，省略大量错误处理）：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <pthread.h>
#include <fcntl.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <linux/videodev2.h>

// ===== 数据结构 =====
typedef struct {
    int fd;                  // 设备文件描述符
    void* buffers[4];        // 内存映射缓冲区
    int buf_count;
    int width, height;
    unsigned char* latest_frame;  // 最新帧
    pthread_mutex_t mutex;        // 互斥锁
    volatile int stop;            // 退出标志（volatile ≠ atomic，不完全安全）
    pthread_t thread;             // 线程句柄
} CameraSource;

// ===== 打开相机（V4L2 手动 ioctl，至少 10 个步骤）=====
int camera_open(CameraSource* cam, const char* device, int w, int h) {
    // 1. open() 设备文件
    cam->fd = open(device, O_RDWR);
    if (cam->fd < 0) return -1;

    // 2. 查询设备能力
    struct v4l2_capability cap;
    ioctl(cam->fd, VIDIOC_QUERYCAP, &cap);

    // 3. 设置格式
    struct v4l2_format fmt = {0};
    fmt.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    fmt.fmt.pix.width = w;
    fmt.fmt.pix.height = h;
    fmt.fmt.pix.pixelformat = V4L2_PIX_FMT_MJPEG;  // MJPG
    ioctl(cam->fd, VIDIOC_S_FMT, &fmt);

    // 4. 设置帧率
    struct v4l2_streamparm parm = {0};
    parm.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    parm.parm.capture.timeperframe.numerator = 1;
    parm.parm.capture.timeperframe.denominator = 60;
    ioctl(cam->fd, VIDIOC_S_PARM, &parm);

    // 5. 请求缓冲区
    struct v4l2_requestbuffers req = {0};
    req.count = 1;  // BUFFERSIZE = 1
    req.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    req.memory = V4L2_MEMORY_MMAP;
    ioctl(cam->fd, VIDIOC_REQBUFS, &req);
    cam->buf_count = 1;

    // 6. mmap 映射缓冲区
    struct v4l2_buffer buf = {0};
    buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    buf.memory = V4L2_MEMORY_MMAP;
    buf.index = 0;
    ioctl(cam->fd, VIDIOC_QUERYBUF, &buf);
    cam->buffers[0] = mmap(NULL, buf.length, PROT_READ | PROT_WRITE,
                            MAP_SHARED, cam->fd, buf.m.offset);

    // 7. 入队缓冲区
    ioctl(cam->fd, VIDIOC_QBUF, &buf);

    // 8. 开启流
    enum v4l2_buf_type type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
    ioctl(cam->fd, VIDIOC_STREAMON, &type);

    // 9. 分配最新帧缓存
    cam->latest_frame = malloc(w * h * 3);
    cam->width = w;
    cam->height = h;

    // 10. 初始化互斥锁
    pthread_mutex_init(&cam->mutex, NULL);

    return 0;
}

// ===== 采集线程 =====
void* capture_thread(void* arg) {
    CameraSource* cam = (CameraSource*)arg;

    while (!cam->stop) {
        struct v4l2_buffer buf = {0};
        buf.type = V4L2_BUF_TYPE_VIDEO_CAPTURE;
        buf.memory = V4L2_MEMORY_MMAP;

        // DQBUF：从驱动取一帧
        if (ioctl(cam->fd, VIDIOC_DQBUF, &buf) < 0) {
            usleep(1000);
            continue;
        }

        // 复制到 latest_frame
        pthread_mutex_lock(&cam->mutex);
        memcpy(cam->latest_frame, cam->buffers[buf.index], buf.bytesused);
        pthread_mutex_unlock(&cam->mutex);

        // QBUF：归还缓冲区
        ioctl(cam->fd, VIDIOC_QBUF, &buf);
    }
    return NULL;
}

// ===== 启动采集 =====
void camera_start(CameraSource* cam) {
    cam->stop = 0;
    pthread_create(&cam->thread, NULL, capture_thread, cam);
}

// ===== 读取最新帧 =====
int camera_read(CameraSource* cam, unsigned char* out) {
    pthread_mutex_lock(&cam->mutex);
    memcpy(out, cam->latest_frame, cam->width * cam->height * 3);
    pthread_mutex_unlock(&cam->mutex);
    return 0;
}

// ===== 关闭相机 =====
void camera_close(CameraSource* cam) {
    cam->stop = 1;
    pthread_join(cam->thread, NULL);
    ioctl(cam->fd, VIDIOC_STREAMOFF, ...);
    munmap(cam->buffers[0], ...);
    close(cam->fd);
    free(cam->latest_frame);
    pthread_mutex_destroy(&cam->mutex);
}
```

### C++ 版本对应的代码量：

```cpp
// 上面 150+ 行的 C 代码，在 C++ 里压缩成：
CameraSource cam(config);
cam.Open(&error);
// ... 采集 ...
cam.ReadLatest(&frame, nullptr, nullptr);
cam.Close();
// 就这 4 行。OpenCV 替你做掉了 V4L2 的全部 ioctl/mmap 脏活。
```

### 对比总结：

| 项目 | C（V4L2 + pthread） | C++（OpenCV + std::thread） |
|------|---------------------|---------------------------|
| 打开相机 | 10+ 个 ioctl 调用 | `cap_.open(device, api)` |
| 设置格式 | `VIDIOC_S_FMT` 手动填结构体 | `cap_.set(CAP_PROP_FOURCC, ...)` |
| 帧缓冲区 | mmap + VIDIOC_QBUF/DQBUF | OpenCV 内部处理 |
| 多线程 | pthread_create/join | std::thread + thread_ |
| 互斥锁 | pthread_mutex_lock/unlock | std::lock_guard 自动 |
| 错误处理 | 每个 ioctl 判断返回值 | OpenCV 统一异常/返回值 |
| 内存管理 | malloc/free + munmap + close | RAII 自动释放 |
| 总代码量 | ~150 行（简化版） | ~50 行（完整版） |

**核心差距不是语法，是封装层次。** OpenCV 帮你做了 V4L2 的全套脏活，C++ 的 RAII 帮你做了资源管理的所有脏活。你只需要关注业务逻辑。

## 12. 小结

本章的核心收获：

1. **CameraSource 的设计原则：对外 3 函数，对内 1 线程。** 调用者不需要知道里面有个线程在跑。
2. **独立线程采集 = 采集和主循环解耦。** 采集线程不停拿帧，主线程只管处理，互不阻塞。
3. **BUFFERSIZE = 1 保证实时性。** 只保留最新帧，旧帧直接丢掉——打靶场景宁可丢帧也不能延迟。
4. **std::lock_guard = RAII 在多线程的体现。** 构造加锁，析构解锁，绝不会忘解锁。
5. **线程安全退出三件套：atomic 标志 + join + 资源释放。** stop_.store(true) → thread_.join() → cap_.release()。
6. **C++ + OpenCV 替你省掉了 100+ 行 V4L2 ioctl 代码。** 这不是一个语法糖的问题，是封装抽象能力的差别。

## 13. 练习：写一个简化版相机采集器

在电脑上新建 `practice_camera.cpp`（如果没接摄像头也可以用视频文件测试）：

```cpp
#include <iostream>
#include <thread>
#include <mutex>
#include <atomic>
#include <string>
#include <opencv2/core.hpp>
#include <opencv2/videoio.hpp>

// ===== 第一步：定义一个简化版 CameraSource =====
class SimpleCamera {
public:
    bool Open(int device_index, std::string* error) {
        if (!cap_.open(device_index)) {
            if (error) *error = "cannot open camera " + std::to_string(device_index);
            return false;
        }
        cap_.set(cv::CAP_PROP_BUFFERSIZE, 1);

        stop_.store(false);
        thread_ = std::thread(&SimpleCamera::Loop, this);
        return true;
    }

    void Close() {
        stop_.store(true);
        if (thread_.joinable()) {
            thread_.join();
        }
        cap_.release();
    }

    bool ReadLatest(cv::Mat* frame) const {
        std::lock_guard<std::mutex> lock(mutex_);
        if (latest_.empty()) return false;
        *frame = latest_.clone();   // clone() = 深拷贝（练习用）
        return true;
    }

    int frame_count() const { return seq_; }

private:
    void Loop() {
        while (!stop_.load()) {
            cv::Mat frame;
            if (!cap_.read(frame) || frame.empty()) {
                std::this_thread::yield();
                continue;
            }
            std::lock_guard<std::mutex> lock(mutex_);
            latest_ = std::move(frame);
            ++seq_;
        }
    }

    cv::VideoCapture cap_;
    mutable std::mutex mutex_;
    cv::Mat latest_;
    std::atomic<bool> stop_{false};
    std::thread thread_;
    int seq_ = 0;
};

// ===== 第二步：主程序 =====
int main() {
    SimpleCamera cam;
    std::string error;

    // 如果没有摄像头，把下面改成 cv::VideoCapture 可以打开的视频文件路径
    if (!cam.Open(0, &error)) {
        std::cerr << error << "\n";
        std::cerr << "(Try changing device index to 1 or 2)\n";
        return 1;
    }

    std::cout << "Camera opened. Collecting frames for 3 seconds...\n";

    // 采集 3 秒钟
    auto start = std::chrono::steady_clock::now();
    cv::Mat frame;
    while (std::chrono::duration<double>(
               std::chrono::steady_clock::now() - start).count() < 3.0) {
        if (cam.ReadLatest(&frame)) {
            // 正常情况下这里做推理
            std::this_thread::sleep_for(std::chrono::milliseconds(10));
        }
    }

    std::cout << "Frames captured: " << cam.frame_count() << "\n";
    cam.Close();
    std::cout << "Camera closed. Done.\n";
    return 0;
}
```
