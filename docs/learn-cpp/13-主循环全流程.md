## main 函数从头到尾：7 个步骤

打开 `src/main.cpp`，跟着走一遍。

### Step 1：解析命令行参数

```cpp
AppConfig config;
if (!ParseCommandLine(argc, argv, &config)) {
    return argc > 1 ? 1 : 0;
}
```

`ParseCommandLine` 把命令行参数（`--camera /dev/video73 --serial_port /dev/ttyUSB0 ...`）填进 `AppConfig` 结构体。没提供参数就用默认值（都在 `config.hpp` 里写好了）。

如果用户只是运行 `./rkfast_target` 不加任何参数，打印用法说明后退出（argc==1 时返回 0，表示正常退出不是报错）。

### Step 2：设置 OpenCV 线程数

```cpp
cv::setNumThreads(std::max(1, config.opencv_threads));
cv::setUseOptimized(true);
```

OpenCV 底层有些操作（颜色转换、resize）会自动开多线程。但我们已经有独立线程做推理和采集了，OpenCV 再开一堆线程反而抢 CPU。默认 `opencv_threads=1`，意思是"OpenCV 你自己别开多线程"。

### Step 3：CPU 亲和性绑定

```cpp
std::string affinity_error;
if (!config.main_affinity.empty() &&
    !BindCurrentThread(config.main_affinity, &affinity_error)) {
    std::cerr << "main affinity warning: " << affinity_error << "\n";
}
```

给当前线程（main 线程）绑定 CPU 核心。RK3576 有多个核心（4*A72 + 4*A53 + 1*M0），手动分配能避免线程在不同核心之间跳来跳去（cache 会冷掉）。

绑定失败只打印警告，不退出 -- 配置错了程序还能跑，别让一个不必要的功能挡住主逻辑。

### Step 4：打开相机（创建采集线程）

```cpp
std::string error;
CameraSource camera(config);
if (!camera.Open(&error)) {
    std::cerr << error << "\n";
    return 1;
}
```

`CameraSource::Open` 做了两件事：
1. 打开 `/dev/video73`（或你指定的相机设备）
2. **启动独立的采集线程** `CaptureLoop`，在后台不停读帧存到 `latest_` 里

从这时起，相机线程就开始跑了。它独立于 main 线程，你不管它它也一直在采集。

### Step 5：创建 RKNN 检测器 -> 预热 -> 启动推理线程

```cpp
auto detector = std::make_unique<RknnDetector>(config);
if (!detector->Open(&error)) {
    std::cerr << error << "\n";
    return 1;
}
if (!detector->Warmup(config.warmup_runs, &error)) {
    std::cerr << error << "\n";
    return 1;
}

DetectorWorker worker(std::move(detector), config.detector_affinity);
worker.Start();
```

分四小步：
1. **创建** RknnDetector 对象（智能指针）
2. **Open**：加载 RKNN 模型，配置 NPU 输入输出
3. **Warmup**：跑 3 次预热推理。NPU 第一次跑会很慢（要初始化内部缓存），预热后性能才稳定
4. **转移所有权**：`std::move(detector)` 把 RknnDetector 交给 DetectorWorker。此后 detector 指针变 nullptr，不能再用了。DetectorWorker 是推理线程的包装，调用 `Start()` 就启动后台推理线程

从这时起，三个线程全部就绪：
- **Camera 线程**：后台不停采集帧
- **Detector 线程**：后台等待推理任务，来一个做一个
- **Main 线程**：正要进入主循环

### Step 6：创建精修器 + 跟踪器 + 输出器

```cpp
RectRefiner refiner(config);
RectTracker tracker(config);
AimWriter writer(config);
if (!writer.Open(&error)) {
    std::cerr << error << "\n";
}
```

这三个没有独立线程，都跑在 main 线程里。它们的数据处理很快（微秒级到毫秒级），不需要独立线程。

`writer.Open` 可能失败（比如你指定的串口设备不存在），但这不影响程序运行 -- 失败了 writer 的 `fd_` 保持 -1，Send 会自动走 stdout 通道。所以失败只打日志，不退出。

### Step 7：主循环

```cpp
std::cout << "running; press q in the debug window to exit\n";
while (true) {
    // ======= 见下一节详解 =======
}
```

无穷循环，直到用户按下 `q` 键退出。循环内部是整篇文章的重点，下面单独展开。

## 主循环内部逻辑：一帧的完整处理流程

主循环每跑一圈，就是处理一帧数据。我把它拆成 7 个小步。

### 7-1：读最新帧（丢旧帧策略）

```cpp
cv::Mat frame;
double frame_ts = 0.0;
uint64_t frame_seq = 0;
if (!camera.ReadLatest(&frame, &frame_ts, &frame_seq) || frame.empty()) {
    continue;   // 没帧就在这打转，等相机线程产出帧
}
if (frame_seq == last_frame_seq) {
    continue;   // 这一帧已经处理过了，跳过
}
last_frame_seq = frame_seq;
```

`ReadLatest` 拿到的**永远是最新的一帧**。如果相机线程已经采集了 5 帧但主循环还没来得及处理，`ReadLatest` 直接返回第 5 帧，前 4 帧直接丢弃。

这个"丢旧帧"策略是实时系统的常规操作。我们不关心每一帧都处理到，只关心处理到的帧是最新的。旧帧的 AIM 坐标已经过时了，发了也没用。

`frame_seq` 是递增的帧序号，用来判断当前帧是不是已经处理过了。

注意：这里没有任何 `sleep` 或等待。如果没新帧就立即 continue 重试，榨干 CPU 来换最低延迟。

### 7-2：取推理结果（非阻塞）

```cpp
const auto result = worker.LatestResult();
bool new_result = result.seq != 0 && result.seq != last_result_seq;
std::optional<Detection> new_detection;
if (new_result) {
    last_result_seq = result.seq;
    new_detection = result.detection;
    infer_fps = result.infer_fps;
    latest_timings = result.timings;
    detect_skip = tracker.Snapshot().active ? config.detect_interval_locked : 0;
}
```

`worker.LatestResult()` 也是非阻塞的 -- 它只是读一下推理线程的最新输出，不等待。返回的 `result` 是一个 `InferResult` 结构体。

`result.seq != 0 && result.seq != last_result_seq` 是两个判断：
- `seq != 0`：确实有推理结果（0 是初始值，表示还没跑过推理）
- `seq != last_result_seq`：这是一个**新的**推理结果（不是上一帧拿过的那个）

如果满足这两个条件，说明有新的检测结果来了。`new_detection` 可能是一个 `Detection`（检测到了），也可能是 `std::nullopt`（推理跑了但没检测到目标）。

**关键一行 -- detect_skip 的设置：**

```cpp
detect_skip = tracker.Snapshot().active ? config.detect_interval_locked : 0;
```

这是"跳过检测"策略的核心。后面单独讲。

### 7-3：决定是否做 ROI 精修

```cpp
std::optional<Box> guide_box = new_detection.has_value()
                                   ? std::optional<Box>(new_detection->box)
                                   : tracker.PriorBox();
std::optional<RefinedRect> refined;
if (guide_box.has_value()) {
    auto snapshot = tracker.Snapshot();
    const std::optional<cv::Point2f> ref_center =
        snapshot.active ? std::optional<cv::Point2f>(snapshot.center)
                        : std::nullopt;
    refined = refiner.Refine(frame, *guide_box, ref_center);
}
```

精修需要一个"引导框"（guide_box）来知道在哪块区域做图像处理。引导框的来源优先级：

1. **有新的检测结果** → 用检测框（最新，最可信）
2. **没有新检测，但跟踪器有先验框** → 用跟踪器预测的位置（PriorBox）
3. **都没有** → guide_box 为空，不精修

如果有引导框，就调 `refiner.Refine()` 在当前帧的引导区域做二值化+轮廓搜索，得到一个更精准的 `RefinedRect`。`ref_center` 是跟踪器已知的目标中心，用来在多个轮廓里挑最靠谱的那个。

### 7-4：更新跟踪器（四选一的优先级决策）

```cpp
bool updated = false;
if (refined.has_value()) {
    tracker.Update(*refined, frame_ts, frame.size(),
                   new_detection.has_value() ? "roi+rknn" : "roi");
    updated = true;
} else if (new_detection.has_value()) {
    tracker.Update(*new_detection, result.timestamp, frame.size(), "rknn");
    updated = true;
} else if (new_result) {
    tracker.MarkDetectMiss(result.timestamp, frame.size());
    updated = true;
}

if (!updated) {
    tracker.Predict(frame_ts, frame.size());
}
```

这是整个管线**最核心的决策**。四个分支按优先级排列：

| 优先级 | 条件 | 操作 | source 标签 | 含义 |
|--------|------|------|-------------|------|
| 1（最好） | 精修成功 + 有新检测 | `Update(RefinedRect)` | `roi+rknn` | 检测框+精修联合，最佳质量 |
| 2 | 精修成功但无新检测 | `Update(RefinedRect)` | `roi` | 纯精修，靠图像处理维持跟踪 |
| 3 | 无精修但有新检测 | `Update(Detection)` | `rknn` | 纯 RKNN 检测 |
| 4 | 推理结果到了但没检测到 | `MarkDetectMiss` | -- | 告诉跟踪器"这帧确实没目标"，跟踪器内部 misses++ |
| 5（最差） | 推理结果都没到 | `Predict` | -- | 纯预测，跟踪器用自己的速度模型推算目标位置 |

为什么这么排？

- **精修+检测**最好：既有 NPU 的"智慧"（知道这是什么），又有图像处理的"精细"（轮廓级定位）
- **纯精修**其次：NPU 推理慢（几十毫秒），但精修很快（几毫秒）。在两帧推理之间，精修可以维持跟踪
- **纯检测**第三：没有精修可用，退回到原始检测框
- **MarkDetectMiss**：推理跑了但没结果，这是重要信息 -- "确定没有"和"不知道有没有"是不同的
- **Predict**：啥都没有，跟踪器自己猜一个位置

### 7-5：提交新推理任务（非阻塞）

```cpp
const TrackSnapshot snapshot = tracker.Snapshot();
if (!worker.Busy()) {
    const bool need_detection =
        !snapshot.active || snapshot.misses > 0 || detect_skip <= 0;
    if (need_detection) {
        worker.Submit(frame, tracker.PriorBox());
    } else {
        --detect_skip;
    }
}
```

这里的逻辑是：**只在推理线程空闲时才提交新任务**。

`worker.Busy()` 返回 true 表示推理线程正在处理上一帧。此时不提交新任务 -- 提交了也没用，线程没空做。

如果线程空闲，判断是否需要提交：
- `!snapshot.active`：没有活跃目标，必须检测（搜索模式）
- `snapshot.misses > 0`：有目标但丢了好几帧，重新检测确认
- `detect_skip <= 0`：跳帧计数用完了，该检测了

`worker.Submit(frame, tracker.PriorBox())` 把当前帧和先验框发给推理线程。注意这是**非阻塞**的 -- Submit 只是把数据拷过去，立即返回。

### 7-6：发送 AIM 输出

```cpp
writer.Send(snapshot, frame.cols, frame.rows);
```

一行搞定。节流、通道选择全在 Send 内部处理好了，调用者不操心。

### 7-7：FPS 统计和调试窗口

```cpp
const double now = NowSeconds();
frame_fps = SmoothValue(frame_fps, 1.0 / std::max(1e-6, now - last_loop), 0.10);
last_loop = now;

if (config.stats_interval > 0.0 && now - last_stats >= config.stats_interval) {
    std::ostringstream stats;
    stats << "stats frame_fps=" << cv::format("%.1f", frame_fps)
          << " infer_fps=" << cv::format("%.1f", infer_fps)
          << " pre=" << cv::format("%.1f", latest_timings.preprocess_ms) << "ms"
          << " rknn=" << cv::format("%.1f", latest_timings.rknn_ms) << "ms"
          << " post=" << cv::format("%.1f", latest_timings.postprocess_ms) << "ms"
          << " select=" << cv::format("%.1f", latest_timings.select_ms) << "ms"
          << " total=" << cv::format("%.1f", latest_timings.total_ms) << "ms"
          << " state=" << snapshot.state
          << " conf=" << cv::format("%.2f", snapshot.conf);
    std::cout << stats.str() << "\n";
    last_stats = now;
}

if (config.show_window) {
    cv::imshow("rkfast_target", DrawDebug(frame, snapshot, frame_fps, infer_fps));
    const int key = cv::waitKey(1);
    if (key == 27 || key == 'q' || key == 'Q') {
        break;
    }
}
```

FPS 用指数平滑（EMA）计算：`frame_fps = 0.9 * 上一次 + 0.1 * 最新值`。这样 FPS 不会因为某一帧卡了就在显示上剧烈抖动。

统计信息每隔 `stats_interval` 秒（默认 1 秒）打印一次。

调试窗口只在 `show_window=true` 时显示。按 `q` 或 `Esc` 键退出。

## 跳过检测策略：detect_skip 和 detect_interval_locked

这是保持高 FPS 的关键技巧。NPU 推理要花几十毫秒，如果每帧都推理，主循环会被推理速度拖慢。但如果一直不推理，目标移动了就找不到。

解决方案：**如果目标已经锁定了，不需要每帧都推理**。

```cpp
// 收到新推理结果时设置 detect_skip
detect_skip = tracker.Snapshot().active ? config.detect_interval_locked : 0;

// 主循环提交任务时判断
const bool need_detection =
    !snapshot.active ||           // 没目标，必须检测
    snapshot.misses > 0 ||        // 目标丢了，重新检测
    detect_skip <= 0;             // 跳帧计数用完了，该检测了

if (need_detection) {
    worker.Submit(frame, tracker.PriorBox());
} else {
    --detect_skip;  // 跳过这一帧，计数器 -1
}
```

默认 `detect_interval_locked = 2`。意思是：

```
有目标时：每收到一次推理结果就跳过 2 帧
         → 推理一次 → 跳2帧 → 跳1帧 → 推理一次 → ...
         → 实际上是每 3 帧推理一次 → 如果帧率 60fps，推理 20fps
         → 但中间跳过的帧用 ROI 精修维持跟踪（精度损失很小）

没目标时：detect_skip=0，每帧都推理
         → 尽快找到目标
```

为什么 ROI 精修能弥补跳帧？因为精修是纯图像运算（几毫秒），比 NPU 推理（几十毫秒）快得多。在 2 帧间隔内目标移动距离很小，精修的轮廓搜索足以追踪。

## 三线程协作图

```
时间轴 ──────────────────────────────────────────────────────>

Camera 线程 ──[采帧1]──[采帧2]──[采帧3]──[采帧4]──[采帧5]──→
               ↓         ↓         ↓         ↓         ↓
            存入latest_（覆盖旧帧）

Detector 线程 ────空闲────[推理帧N]────────空闲────[推理帧N+3]──→
                          ↑ 几十ms              ↑
                          Submit()             Submit()

Main 线程 ──[取最新帧]──[精修]──[跟踪]──[AIM输出]──[取最新帧]──→
              ↑                                    ↑
           ReadLatest()                       ReadLatest()
           (不阻塞，拿最新)                    (不阻塞，拿最新)
              ↓
          Submit() 非阻塞，发了就继续跑
              ↓
          LatestResult() 非阻塞，有就取，没就算
```

要点：
1. **三个线程独立运行**，互不等待
2. **Camera 线程**：独自采集，写入共享缓冲区（latest_）
3. **Detector 线程**：等待任务队列，来一个做一个，结果写入共享变量（latest_result_）
4. **Main 线程**：从两个共享区读数据，非阻塞，没有就跳过
5. **唯一同步点**：`mutex_` 保护的共享数据区域

## 程序退出流程

```cpp
writer.Close();          // 1. 先关输出，发完最后一帧 AIM
worker.Stop();           // 2. 停止推理线程，等当前推理跑完
camera.Close();          // 3. 关闭相机，停止采集线程
cv::destroyAllWindows(); // 4. 销毁 OpenCV 窗口
return 0;
```

退出顺序很重要：
1. **先关 writer**：如果不关，worker 和 camera 都停了以后 writer 可能还在尝试输出，发出去的也是过时数据
2. **再关 worker**：Stop 会设置 `stop_=true`，推理线程跑完当前任务后自己退出
3. **最后关 camera**：Stop 设置 `stop_=true`，采集线程退出循环，释放相机资源

三个类的析构函数都会自动调 Close，所以就算你不显式调用，程序 exit 时也会自动清理。但显式调用既安全又清晰。

## 统计输出解读

运行时会看到类似这样的输出：

```
stats frame_fps=61.3 infer_fps=22.1 pre=1.2ms rknn=38.5ms post=2.1ms select=0.3ms total=42.1ms state=TRACKING conf=0.95
```

每个字段的含义：

| 字段 | 含义 | 典型值 | 说明 |
|------|------|--------|------|
| `frame_fps` | 主循环帧率 | 60+ | 读帧+精修+跟踪+输出这一圈的速度。通常等于相机帧率 |
| `infer_fps` | 推理帧率 | 20-25 | 检测线程跑推理的速度。受 NPU 和跳帧策略影响 |
| `pre` | 预处理耗时 | 1-3ms | RGA 做缩放+颜色转换的时间 |
| `rknn` | RKNN 推理耗时 | 35-45ms | NPU 推理本身的时间（这是大头） |
| `post` | 后处理耗时 | 1-3ms | 解码输出矩阵+NMS 的时间 |
| `select` | 选择检测耗时 | 0.1-0.5ms | ChooseDetection 挑最佳检测的时间 |
| `total` | 推理总耗时 | = pre+rknn+post+select | 从提交到拿到结果的完整时间 |
| `state` | 跟踪状态 | SEARCHING/TRACKING/LOST | 跟踪器状态机 |
| `conf` | 置信度 | 0.00-1.00 | 当前跟踪目标的置信度 |

注意 `frame_fps > infer_fps` 是正常的（60 vs 22）。Main 线程比推理线程快得多，因为它只是读读数据、调调精修、发发串口，没有 NPU 推理的重活。中间跳过的帧靠 ROI 精修和 Predict 维持跟踪。

### 项目架构层

| 模块 | 核心职责 | 在哪章 |
|------|----------|--------|
| `CameraSource` | 后台采集线程，ReadLatest 拿最新帧 | （属于前面章节） |

### 设计模式层

这个项目用到了几个反复出现的设计模式：

1. **RAII（资源获取即初始化）**：构造时打开资源，析构时自动释放。CameraSource、RknnDetector、AimWriter 都是这样
2. **生产者-消费者**：Camera 线程生产帧，Main 线程消费帧；Main 线程提交任务，Detector 线程消费任务
3. **非阻塞通信**：Submit、LatestResult、ReadLatest 全都是非阻塞的，不等待，不卡顿
4. **优先级决策**：精修 > 检测 > 标记丢失 > 纯预测，数据从哪来不重要，优先用最好的
5. **跳帧加速**：有目标时跳过不必要的推理，用快速精修填补间隙

## 速查表：一帧内调了哪些函数

| 顺序 | 函数调用 | 阻塞？ | 做什么 |
|------|----------|--------|--------|
| 1 | `camera.ReadLatest()` | 否 | 拿到最新帧 |
| 2 | `worker.LatestResult()` | 否 | 拿推理结果（可能是旧的） |
| 3 | `tracker.PriorBox()` | 否 | 拿先验框 |
| 4 | `refiner.Refine()` | 是（几ms） | ROI 精修 |
| 5 | `tracker.Update()/MarkDetectMiss()/Predict()` | 否（<1us） | 更新跟踪状态 |
| 6 | `tracker.Snapshot()` | 否 | 拿当前快照 |
| 7 | `worker.Busy()` | 否 | 推理线程忙不忙？ |
| 8 | `worker.Submit()` | 否 | 提交新推理任务（如果闲） |
| 9 | `writer.Send()` | 否（可能几us） | 发出 AIM 协议 |

注意：整个主循环只有 `Refine` 可能稍微花点时间（几毫秒），其他全是非阻塞的即时操作。这就是为什么 frame_fps 能达到 60+ -- 主循环本身非常轻量。
